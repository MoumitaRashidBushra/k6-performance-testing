# Self Cash-in through Stripe — Test Cases (Lean, per test-design SKILL.md)

## Scope Summary

Core business promise: an authenticated, **active Customer** can top up their DMoney wallet via a Stripe card payment, with the server enforcing the amount range (10–10,000, from the `Deposit` Commission config), the 10,000 BDT wallet cap, and a spoof-proof, idempotent ledger credit tied 1:1 to a verified Stripe `PaymentIntent`. Verified directly against `stripeCashIn.controller.js`. Decision points: role gate, status gate, amount-range gate, wallet-cap gate (create-intent); PI-status gate, anti-spoofing gate, idempotency gate (confirm). Named regression-affected consumer: `dmoney-web-react/src/app/customer/cash-in-bank/page.tsx`.

Real DB data: active Customer `01686606902` (balance ≈ 5970.50), active Customer `01686606903` (balance ≈ 11449.50, already over cap), pending Customer `01504474888`, active Agent `01686606901`. Deposit Commission config: `min_txn_amount=10.00`, `max_txn_amount=10000.00`.

Cases trimmed from an earlier 30/27-item list per SKILL.md Step 4 (redundancy control) and the Coverage Rules cap — see "Why trimmed" note at the bottom.

## Known Gaps (evidence-backed, not counted in the lean suite above)

These test the **absence of a safeguard** rather than a coded decision branch, so they don't fit the skill's "trace to a decision point" model for the sanity suite — but they're real, code-confirmed risks worth a dedicated exploratory pass or a dev/business sign-off:

| ID | Title | Why it's a real risk |
|---|---|---|
| GAP_001 | Concurrent duplicate confirm requests on the same PaymentIntent | No `sequelize.transaction()`/row lock guards the idempotency check + inserts (lines 160-192) — two simultaneous confirms could both pass `alreadyProcessed` before either writes, risking a double credit |
| GAP_002 | Wallet cap not re-validated between create-intent and confirm | `confirmCashIn` never re-checks the 10,000 BDT cap or amount range that `createPaymentIntent` enforced — balance can end up over cap if it changed in between |
| GAP_003 | Ledger consistency if the 2nd Transactions.create fails after the 1st succeeds | No transaction wrapper around the two inserts — a mid-way failure leaves an orphaned SYSTEM-debit row, and a retry then hits the idempotency check (208) even though the customer was never credited, with no recovery path |

## Why trimmed from 30/27 to 10

- Role-reject + status-reject → merged into TC_SCI_003 (same gate-check pattern, two data rows, one execution)
- Min-reject + max-reject + min-accept + max-accept (4 cases) → merged into TC_SCI_002 (one threshold-boundary case, two thresholds, all four values)
- Non-positive/non-numeric amount (amt≤0) → folded into TC_SCI_002's amount-validation scope rather than kept as its own case (accepted trade-off: this collapses a distinct message branch — "Amount must be a positive number" vs "Minimum cash-in amount is 10 tk" — into one title; call this out explicitly if a tester needs the exact message per branch)
- Ledger-shape, no-commission, trnxId=PI-id, metadata-correctness (4 standalone cases) → folded into the parent flow they belong to (TC_SCI_001, TC_SCI_006) instead of standing alone
- Generic auth-header/JWT-validity check and "JWT identifier maps to no user" 404 → **cut**; both are upstream middleware/lookup guarantees, not decisions this feature owns (SKILL.md Step 2: skip failure modes upstream layers already block)
- Concurrency race, cap-not-rechecked, partial-write inconsistency → moved to "Known Gaps" (real, but test the absence of a safeguard, not an implemented branch)
